> Статус: PROPOSAL, не применён. Репозитория AISIX-Cloud рядом нет
> (проверено 2026-09-27: `/home/ernur/AISIX-Cloud` отсутствует,
> `openapi/cp-admin.yaml` в дереве `aisix/` не найден) — ниже точный
> spec-патч, который нужно внести на стороне control plane.
> Основа — реализованная поверхность `aisix-admin::combos_handler`
> (`crates/aisix-admin/src/combos_handler.rs`), маршруты
> `crates/aisix-admin/src/lib.rs`, OpenAPI
> `crates/aisix-admin/src/openapi.rs` (`Combo`, `ComboModel`, `ComboEntry`).

## 1. Что уже умеет DP (и почему это не новый ресурс)

**Combo — это virtual routing model, а не отдельный ресурс.** Запись
комбо пишется в коллекцию `models`; её `routing`-блок несёт
`strategy` + `targets`. Поэтому:

- новый ресурс в `cp-admin.yaml` **не нужен** и не должен появляться:
  добавление `Combo` как шестого `kind` в `Model` продублировало бы
  уже существующий `routing` и заставило бы пересматривать все
  model-keyed механизмы ради второй записи одного и того же;
- **все поля, которые эта поверхность принимает, уже есть в спеке**:
  `display_name` (управляемое нами `name`), `routing.strategy`,
  `routing.targets[].model` / `.weight` / `.priority` / `.tags`. То есть
  четверка слоёв CP из правила «config knob не зашит, пока его не
  отдаёт control plane» сводится здесь к чеклисту, который уже выполнен
  для `Model`: спека, Go-модель, etcd-проекция и форма уже есть.

Что реально нужно от CP — перестать быть источником истины для combos
и начать быть клиентом gateway Admin API.

## 2. Точный spec-патч для `openapi/cp-admin.yaml`

**Изменений схемы не требуется.** Ни одно поле, принимаемое
`POST /admin/v1/combos`, не является для спеки новым, и ни одно не
переименовывается. Существующие ограничения спеки, которые поверхность
унаследовала, закрывают две дыры, о которых стоит знать явно:

1. `Model.routing` и прямые upstream-поля — взаимоисключающие
   (`oneOf`). Комбо пишет `display_name` + `routing` и **не** пишет
   `provider` / `model_name` / `provider_key_id`. Форма CP обязана
   скрывать прямые поля у модели с `kind: routing`, иначе CP сохранит
   документ, который DP-loader отвергнет как невалидный.
2. `routing.targets[].model` — **имя**, не id. В режиме standalone
   (resources-файл) id резолвить нечем: DP отвергает `model_id` в
   файле ресурсов явным сообщением. Это ровно зарегистрированная ось
   расхождения «reference style: names here vs UUIDs in the CP» — она
   уже есть в `openapi/cross-plane-allowlist.yaml`, новой записи не
   требует.

## 2a. Стратегии: два словаря на проводе, одно значение в хранилище

**Счёт, который надо зафиксировать первым: в etalon-шаблоне 20 стратегий,
а не 19.** `omniroute/src/shared/constants/routingStrategies.ts` →
`ROUTING_STRATEGY_VALUES` (строки 1–22) содержит 20 значений; «19» из
`AGENTS.md` etalon-репозитория — это прозаический перечень, который
опускает `quota-weighted`. Опора на список массива, а не на прозу.

`POST`/`PATCH /admin/v1/combos` теперь принимают **оба** словаря:

- **6 собственных значений gateway** (`round_robin`, `consistent_hash`,
  `failover`, `least_cost`, `least_latency`, `least_busy`) — то, что несёт
  routing-модель и что возвращает `GET`;
- **5 имён шаблона**, каждое из которых **переводится на входе** в
  стратегию, которая его реализует, и хранится уже под именем gateway:

  | Имя шаблона | Стратегия gateway | Почему это честно |
  | --- | --- | --- |
  | `priority` | `failover` | «предпочитай старший priority, проваливайся дальше по отказу». `failover` стартует с первой цели и двигается только по отказу, а список целей **сначала** разбивается на priority-тиры (`partition_by_priority`) — тир ниже достигается, только когда весь тир выше отказал. Расхождение: тирация — свойство модели, а не следствие имени стратегии, поэтому без явного `priority` список целей — один тир и ведёт себя как обычный first-then-failover |
  | `weighted` | `round_robin` | «доля трафика пропорциональна весу цели». `round_robin` здесь — **smooth weighted** round-robin (алгоритм nginx, `aisix-proxy/src/routing.rs::wrr_pick`), его долгосрочная доля — ровно это. Отдельного варианта `weighted` в enum **нет намеренно**: он удалён и слит с `round_robin` (AISIX-Cloud#1206, закреплено тестом `removed_weighted_strategy_and_sticky_flag_are_rejected`). **Расхождение, названное явно:** etalon рисует на каждый запрос `secureRandomFloat() * totalWeight` (`open-sse/services/combo/targetSorters.ts::selectWeightedTarget`) — независимая выборка; smooth WRR — детерминированная ротация. Доли за время совпадают, закон выбора за запрос — нет; `stickyWeightedLimit` etalon здесь соответствия не имеет |
  | `round-robin` | `round_robin` | То же имя для того же алгоритма. Единственное добавление etalon — `stickyRoundRobinLimit`, и здесь липкость — отдельная стратегия (`consistent_hash`), а не ручка на комбо |
  | `fill-first` | `failover` | Собственная ветка etalon для него сохраняет порядок по priority и больше ничего (`applyStrategyOrdering.ts`, ветка `fill-first` логирует «preserving priority order» и список не трогает). Это `failover` под вторым именем |
  | `cost-optimized` | `least_cost` | Самая дешёвая разрешённая цена по возрастанию — то же правило и тот же источник цены, что `sortTargetsByCost` в etalon |

**Остальные 15 имён отвергаются по имени, а не мапятся:**
`random`, `strict-random`, `p2c`, `least-used`, `headroom`, `context-relay`,
`context-optimized`, `cache-optimized`, `reset-aware`, `reset-window`,
`quota-weighted`, `auto`, `lkgp`, `fusion`, `pipeline`.

Отказ — не недосмотр, а решение, и вот почему каждое из них не имеет
честного дома (полный разбор с file:line — в doc-комментарии
`REFUSED_TEMPLATE_STRATEGIES` в `crates/aisix-admin/src/combos_handler.rs`):

- `random` / `strict-random` / `p2c` — **стохастические** (перетасовка,
  колода без возврата, выборка из двух по качеству). Все стратегии, которые
  можно было бы взять взамен, здесь **детерминированные**: `round_robin`
  крутит счётчик, `consistent_hash` прикалывает ключ к одной цели. Маппинг
  случайного выбора на детерминированный — самое чистое враньё: оператор
  просил распределять трафик, а получает липкость, или наоборот.
- `p2c` вдобавок **не метрика нагрузки**: etalon считает
  `success_rate + 1/log10(latency+10)` минус штраф за breaker
  (`getP2CTargetScore`), тогда как `least_busy` ранжирует по
  in-flight ÷ weight, а `least_latency` — по EWMA задержки. Ни то ни другое
  не тот счёт, и обе теряют рандомизацию, ради которой p2c и существует.
- `least-used` считает запросы **кумулятивно за жизнь комбо**
  (`sortTargetsByUsage` по `metrics.byTarget[].requests`). Gateway такого
  счётчика не ведёт: `least_busy` читает мгновенный in-flight
  (`ModelRuntimeStatusTracker::in_flight`). Цель, отработавшая миллион
  запросов час назад, там выглядит простаивающей.
- `headroom` — это остаток **лимита**,
  `1 − max(util_5h, util_7d)` по насыщению плановых окон
  (`open-sse/services/combo/headroomRanking.ts`); `least_busy` меряет
  одновременные запросы. «Больше свободной ёмкости» и «меньше занято» —
  разные сигналы, и очередь — только один из них.
- `context-relay` **переносит** разговор при провале: отбирает историю
  сообщений, суммаризует её через handoff-модель и подставляет в новую
  цель (`open-sse/services/contextHandoff.ts`). `consistent_hash` проблему
  обходит, а не решает — прикалывает сессию, чтобы переноса не было. Обещать
  relay и отдать pin — ложь о механизме, а конфиг relay
  (`handoffModel`, `handoffThreshold`, `maxMessagesForSummary`, `relayMode`)
  был бы принят и проигнорирован.
- `reset-aware` / `reset-window` / `quota-weighted` ранжируют по живому
  состоянию квоты на соединение (`quotaStrategies.ts`). Цели gateway — это
  модели, и снапшота квоты на соединение у него нет.
- `auto` — скорер по 16 факторам, выбирающий одну из `rules`/`score`/`cost`/
  `eco`/`latency`/`fast`/`sla-aware`/`sla`/`lkgp` на запрос
  (`open-sse/services/autoCombo/`, `resolveAutoStrategy.ts`). Это выбор
  стратегии, а не стратегия.
- `lkgp` продвигает последнего удачного **провайдера+соединения**
  (`getLKGP`). У gateway нет провайдерских аккаунтов, из которых это
  запоминать: цели — модели.
- `context-optimized` ранжирует по лимиту контекста цели, по убыванию;
  `cache-optimized` прикалывает цель по сродству prompt-кэша
  (`promptCacheAffinity.ts`) — ключ кэша это промпт, а routing-ключ это
  сессия вызывающего, подменять их нельзя.
- `fusion` — параллельный fan-out на панель с **judge-моделью**
  (`open-sse/services/fusion.ts`), то есть форма ensemble, а не порядок
  выбора цели; `pipeline` — многошаговый DAG, у которого каждый шаг может
  называть свою модель (`dispatchPrelude.ts:587`), то есть форма запроса.

**Правило, которым это решено:** имя, меняющее поведение, хуже честного
400. Оператор, выбравший такое имя в выпадающем списке, должен узнать об
отказе, а не обнаружить через месяц, что политика, которую он выбрал,
обслуживалась другой.

**Итог: 5 из 20 стратегий шаблона реализованы, 15 отвергнуты по имени.**
`least_latency` реализована в gateway, но двойника в шаблоне не имеет.

## 2b. Что из этого требует изменений в CP (обязательная половина)

Это **config surface**, доступная пользователю, поэтому по правилу
«config knob не зашит, пока его не отдаёт control plane» DP-половина
**не является поставленной**. Нужен парный CP-пул, четыре слоя:

1. **`openapi/cp-admin.yaml` — новое перечисление.** Либо 5 новых значений
   в существующий enum `routing.strategy`, либо (предпочтительнее)
   отдельное поле-«синоним», если CP не хочет смешивать два словаря в
   одном enum. Затем **регенерация Go-биндингов**. Важно: значения из
   `REFUSED_TEMPLATE_STRATEGIES` в спеке **не добавлять** — CP не должен
   предлагать то, что DP отвергает; иначе форма соберёт документ,
   который сохранится и не пройдёт запись.
2. **Go-модель + валидация запроса** (`internal/cpapi/resources/`): на
   входе разворачивать синоним в каноническое значение стратегии, чтобы в
   etcd всегда лежало каноническое (иначе DP-loader, читающий только
   свои шесть значений, отвергнет строку целиком — а отвергнутая строка
   `models` в `aisix-etcd/src/loader.rs` пропускается молча).
3. **etcd-проекция:** без изменений, **но** новое перечисление в спеке —
   это изменение формы значения, поэтому по правилу «не менять форму
   проецируемого поля на месте» проверить, что у зарегистрированных
   gateway нет проблемы с более старым release, который такое значение не
   знает. Каноническое значение в etcd этому риску не подвержено — ещё
   один довод за вариант «переводить на входе».
4. **Форма + i18n:** выпадающий список шаблона остаётся из 20 (это то,
   что оператор ожидает увидеть), но теперь 5 из них рабочие. Подписи и
   подсказки в `messages/en.json` + `messages/zh.json` — и, обязательно,
   **текст о том, что 15 остальных не поддерживаются**: либо серым в
   списке, либо по пояснению рядом. Список без такого текста вернёт 400
   пользователю, который выбрал `fusion`.
5. **Тесты:** расширить существующий CP↔DP кейс из §3.5 паразией
   «комбо, сохранённое через CP с именем стратегии-синонима, читается DP и
   обслуживается» и «комбо, сохранённое через CP с отвергаемым именем
   стратегии, отклоняется **CP** до записи в etcd, а не падает на
   DP-loader».

Доступа к репозиторию control plane из этой ветки нет, поэтому ничего из
перечисленного здесь не реализовано и в этом PR не поставляется.

## 3. Go-модель / валидация / проекция — чеклист

1. **Схема + биндинги:** без изменений (см. §2). Регенерация Go-биндингов
   из `cp-admin.yaml` не требуется.
2. **Go-модель** (`internal/cpapi/resources/`): без изменений. Комбо —
   это `Model` с `Kind == "routing"`. Новый тип `Combo` на Go-стороне
   вводить не надо: он стал бы вторым представлением `Model` и
   рассинхронизировался бы с ним на первом же переименовании.
3. **Валидация запроса:** добавить в существующий путь сохранения
   `Model` правило «у `kind: routing` непринимаемы `provider`,
   `model_name`, `provider_key_id`» — то, что `oneOf` спеки уже
   выражает, но которое суррогатная модель CP могла обходить.
4. **etcd-проекция:** без изменений. Проекция `Model` уже пишет
   `routing`/`targets`; пере-проекция коллекции не нужна (нет reshape,
   нет нового optional-ключа — ср. `ReprojectMcpAclOnce`, который здесь
   не применим).
5. **Тесты:** CP↔DP Go-интеграция в `e2e/cases/`:
   - комбо, сохранённое **через gateway Admin API** (`POST
     /admin/v1/combos`), читается DP и обслуживается: запрос с
     `model: <combo name>` уходит на один из `models` в `targets`;
   - комбо, сохранённое **через CP** с запрещённым полем, отвергается
     CP до записи в etcd (а не падает на DP-loader);
   - документ с `targets[].model_id` отвергается DP в standalone-режиме
     с внятным сообщением (регрессия подтверждает §2.2).

## 4. Dashboard — чеклист

Главное изменение: combos-экран перестаёт читать/писать собственную
коллекцию и ходит в gateway Admin API.

- **Слой доступа:** заменить вызовы собственного combos-хранилища на
  `GET/POST /admin/v1/combos` и `GET/PATCH/DELETE
  /admin/v1/combos/{id}`. Ответ `ComboEntry` уже содержит `id`, нужный
  для адресного PATCH/DELETE; `PATCH` принимает тело, отличное от
  `id`, так что ответ `GET` можно редактировать и отправлять обратно
  без преобразования.
- **Форма:** поля только `name`, `strategy`, `models[]` (внутри —
  `model`, `weight`, `priority`, `tags`).
  - `strategy` — выпадающий список. Значения **шаблона** (те 20, что
    перечислены в `ROUTING_STRATEGY_VALUES`) — то, что оператор
    ожидает увидеть, — но отправлять можно только рабочие: пять
    переводимых синонимов плюс шесть собственных имён gateway. Список
    канонических значений получать из
    `schemas/resources/routing.schema.json` (definitions
    `RoutingStrategy`), а не дублировать в коде; таблицу перевода
    синонимов — из §2a, а не из памяти.
  - **Важно про read-back:** `GET` возвращает **каноническое** значение, а
    не то имя, которое отправили. Комбо, сохранённое как `priority`,
    читается как `failover`. Форма, которая показывает пользователю
    `priority`, а в базе хранит `failover`, обязана при обратной загрузке
    отображать `failover` — иначе UI покажет «настроено не то». Либо
    форма хранит выбранный синоним у себя (отдельная колонка), либо
    принимает расхождение и показывает каноническое имя.
  - **15 отвергаемых имён** (§2a) нельзя оставлять в списке без
    пояснения: они отвергаются DP с 400. Варианты: серые неактивные
    пункты с подсказкой «не поддерживается этим gateway», или активный
    пункт, который честно показывает 400 с именем поля. Молча принимать и
    терять — прямо запрещённый исход.
  - `models[]` — выбор из существующих **прямых** моделей. Combo-ref
    (вложенные группы) и provider-wildcard в UI не предлагать: DP их
    отвергает, а вложенная группа без guard на циклы — не то, что
    стоит показывать как рабочую опцию.
- **Чего форма НЕ должна отправлять** (DP отвергнет каждое из этих
  полей с 400, называя его): `description`, `displayName`, `config`,
  `allowedProviders`, `allowedModelFamilies`, `system_message`,
  `tool_filter_regex`, `context_cache_protection`, `context_length`,
  `dimensions`, `isActive`, `isHidden`; на уровне шага — `label`,
  `connectionId`, `allowedConnectionIds`, `prompt`,
  `fallbackOnlyOnQuotaExhaustion`, `kind`, `model_id`. Любой из них,
  который сегодня форма умеет рисовать, должен быть убран из combo-режима
  (в режиме редактирования прямой модели он остаётся).
- **i18n:** `messages/en.json` + `messages/zh.json` (обе — правило CP) —
  подписи целевого списка, подсказки стратегий и текст ошибки о поле вне
  контракта.
- **Playwright-тест:** создать комбо → combo-экран показывает его →
  перетащить/переставить цель → сохранить → перезагрузить → порядок и
  веса на месте; ввести поле вне контракта в combo-режиме → форма не
  даёт отправить (или показывает ошибку 400 с именем поля), а не
  «успешно сохраняет и молча теряет».

## 5. Что осталось за CP-стороной (осознанный долг)

Каждое отвергнутое поле — это не баг DP, а отсутствующая функциональность
в routing-модели. Список на будущее, с владельцем на CP-стороне:

| Поле | Что для этого нужно в DP | Заметка |
| --- | --- | --- |
| `config.*` (44+ ключа) | поштучно сопоставить с полями `routing`/`model` либо описать в `cp-admin.yaml` | `maxRetries` и `retries` семантически **не** одно и то же; мапить «похожее» нельзя |
| 15 стратегий из 20 etalon | реализовать алгоритм либо сузить UI | полный разбор по каждому имени — §2a. Реализованы 5 (`priority`, `weighted`, `round-robin`, `fill-first`, `cost-optimized`); отвергаются по имени 15, и для каждой указано, почему ближайшая стратегия gateway считает что-то другое |
| combo-ref / provider-wildcard | guard на циклы + резолв wildcard-шаблонов | вложенность сегодня отвергается осознанно |
| `system_message`, `tool_filter_regex` | поля на `Model` | в `cp-admin.yaml` их нет, значит нет и в etcd |
| `isActive` / `isHidden` | `enabled` на строке `Model` | сегодня у `Model` нет собственного `enabled` |
| `context_length`, `dimensions`, `context_cache_protection` | поля на `Model` | то же |

Каждая строка — отдельная задача DP + парная задача CP. Добавлять поле
«просто чтобы форма могла его нарисовать» нельзя: принятое и
непрочитанное поле читается на консоли как «настроено» и не делает
ничего.

## 6. Contract-check

- Расхождений не добавляет: ни одно поле не переименовано, не удалено и
  не перетипизировано; `Combo` не появляется в спеке как ресурс.
- **Стратегии — исключение, требующее явной регистрации.** 5 новых
  значений enum, принимаемых Admin API, которых нет в `cp-admin.yaml`, —
  это ровно тот случай, который поймает `contract-check.yml`. Либо они
  добавляются в спеку (тогда пятой оси нет), либо расхождение
  «management surface: Admin API принимает пять синонимов стратегии,
  которых нет в перечислении спеки» вносится в
  `openapi/cross-plane-allowlist.yaml` со ссылкой на §2a этого документа.
  Без одного из двух `contract-check` будет красным.
- Если `contract-check.yml` покажет расхождение по путям Admin API —
  это будет расхождение пятой оси («поверхность управления»), её надо
  внести в `openapi/cross-plane-allowlist.yaml` с этой же ссылкой на
  документ; четыре зарегистрированные оси (reference style, tenancy
  scoping, credential custody, CP-derived fields) не затрагиваются.
